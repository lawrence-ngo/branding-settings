Chapter 1
System Overview
The Branding system gives operators control over how their booking pages look and behave. It separates visual identity from content structure, letting each layer be managed independently.

The Two-Layer Model

Every booking page is shaped by two independent layers. They can be mixed and matched freely — switching one doesn't affect the other.

Layer 1
🎨 Brand Kit
Controls the visual identity of the booking page. Defines how the page looks.
Logo Brand name Header color Button color Link color
Layer 2
📄 Content Profile
Controls the booking flow structure. Defines how the page works.
CTA label Field visibility Description length Add-on display Date selector style Checkout layout
Key principle: Brand Kits and Content Profiles are independent. An experience can use the "Acme Corp" brand kit with the "Premium" content profile, or the "Acme Corp" brand kit with a custom content profile — any combination works.

Scope: Account vs Experience

Both layers can be configured at the account level or per-experience.

Scope Brand Kit Content Profile
Account-level Named kits in Branding Settings. Can be assigned to multiple experiences. Edits affect all assigned experiences. Named shared profiles created by the operator (e.g. "Classic," "Premium"). Edits affect all assigned experiences.
Experience-level Each experience selects which brand kit to use. Each experience can have its own private content profile. Edits affect only that experience.

Brand Kits
A Brand Kit is a named collection of visual settings that controls the look and feel of the booking page. An account can have multiple brand kits — useful for operators running multiple brands.

Brand Kit Cards

Brand kits are listed in Branding Settings as cards. Each card shows the kit name, a preview of the header color swatch, and whether it's the account default. A three-dot menu on each card exposes Edit and Archive actions.

Scope warning: Editing a shared brand kit affects every experience using that kit. The kit editor shows how many experiences will be affected before saving.

The Brand Kit Editor

The brand kit editor uses a split-panel layout: a live canvas preview on the left (switchable between mobile and desktop viewports) and a settings panel on the right. The canvas is divided into three tabs: Details, Checkout, and Confirmation — mirroring the actual booking flow steps.

The settings panel is a single accordion of Brand Kit settings: kit name and brand name, header color and logo, button color, link color. There is no section-level navigation inside the brand kit editor — all controls live in the one panel.

Chapter 3
Content Profiles
A Content Profile defines the structure and behavior of the booking flow. Unlike Brand Kits which are purely visual, Content Profiles determine what information is shown, how it's organized, and what actions are available to the guest.

Shared Profiles

A new account starts with a single blank default profile. The operator names it and configures it, and every experience points to it until something else is created. From there, operators can create additional shared profiles in Branding Settings — useful when different experience tiers warrant distinct booking flows.

The illustrative examples below show what shared profiles an operator might create. They aren't shipped defaults — the names, copy, and styling are entirely up to the operator.

Custom (Experience-Scoped) Profiles

An experience can opt out of a shared profile and get its own private content profile. This is called a custom profile. Custom profiles:

  • Are created from within the Experience Editor (not from Branding Settings)
  • Are private to that experience — not assignable to other experiences
  • Can be edited freely without any scope warning (no blast radius)
  • Do not appear in the account-level Content Profiles list
Design decision: Custom profiles are intentionally kept experience-scoped to make iteration frictionless. Since they only affect one experience, operators can experiment without worrying about unintended side effects.

The Experience Editor
The Experience Editor is where operators configure individual experiences. The Design bar at the top is the primary control surface for Brand Kit and Content Profile settings.

The Design Bar

A horizontal bar below the experience title that shows the currently active Brand Kit and Content Profile. It provides quick access to switch either without leaving the editor.

Acme Corp
Content Profile
Classic
Shared profile active. The canvas is in read-only preview mode. The operator can see how the profile looks but can't edit content blocks directly. The "Customize for this experience" CTA is visible in the profile switcher.

Canvas Modes

The experience canvas has two modes depending on whether a custom profile is active:

ModeWhen activeBehavior
Preview mode .preview-mode Shared profile assigned Canvas sections are visible but not clickable/editable. Acts as a passive preview of the shared profile.
Edit mode Custom profile assigned Canvas sections are fully interactive. Clicking opens the right-hand settings panel for that section.

Panel System

The right-hand panel in the experience editor shows different views depending on context. The key views are:

  • custom — the default editor view with canvas sections
  • branding — the brand kit switcher
  • profile — the content profile switcher

Navigation between views is handled by eeSetView(name). When the canvas is in preview mode, clicking any section is blocked by a JS guard — eeOpenPanel() checks for the .preview-mode class before opening a panel.

Chapter 5
The Customization Flow
When an experience operator wants to customize the content profile specifically for their experience, they go through a simple one-time flow. After that, they iterate directly on the canvas with no friction.

Step-by-Step

1
Operator clicks "Customize for this experience"
The design bar shows this CTA only when a shared profile is active. It's the entry point for per-experience customization.
2
Confirmation modal appears
A lightweight modal explains what's about to happen: "This creates a profile built just for this experience. Edits here won't affect any other experiences." No naming required — the profile is always named "Custom", regardless of which shared profile it was created from or which experience it belongs to. The operator can rename it later from inside the profile editor.
3
Profile is created and applied
A new experience-scoped profile is registered. The design bar updates to show the new profile name. The canvas exits preview mode and becomes fully editable.
// createProfileConfirm() does four things: var profileName = 'Custom'; // always "Custom", never derived from the experience name var autoDesc = 'Customized from ' + baseName + ' for ' + expName + '.'; profileConfigs[newProfileId] = { name: profileName, desc: autoDesc, /* ...inherited settings */ }; eeProfile.customized = true; eeProfile.customName = profileName; eeUpdateProfileUI(); // updates design bar + canvas mode
4
Operator edits directly on the canvas
No separate profile editor journey needed. Clicking any section opens the settings panel for that section. Changes are experience-only — no scope warnings, no blast radius.
5
Operator can switch profiles at any time
The "Switch" button in the design bar opens the profile switcher. The switcher lists shared profiles plus the custom one for this experience. Selecting a different profile replaces the current one (the custom profile remains in the switcher for re-selection).

State Machine

The entire design bar + canvas behavior is driven by the eeProfile object. Two boolean states determine everything:

eeProfile state → UI behavior
State A
customized: false
  • Canvas in preview mode (locked)
  • "Customize" CTA visible
  • Profile pill has background
  • Design bar name = shared profile name
State B
customized: true
  • Canvas editable (preview mode off)
  • "Customize" CTA hidden
  • Profile pill background removed
  • Design bar name = customName
No copy proliferation: The first time an operator customizes, a profile is created. Every subsequent edit goes directly to the canvas — no new profile is ever created. This was a deliberate design choice to prevent endless copies accumulating.

Profile Switcher

Accessible via the "Switch" button in the design bar. Lists all available profiles for the experience:

  • The "Use default" option (follows account default automatically)
  • Any shared profiles in the account (e.g. "Classic," "Premium," "Minimal" if the operator has created profiles by those names)
  • The experience's custom profile (if one exists) — always named "Custom", shown with "Custom for this experience" sub-label

Shared profiles in the switcher have a hover-revealed pencil icon that navigates to the profile editor for that profile, with a scope warning noting how many experiences will be affected.

Chapter 6
Developer Reference
Key data structures, functions, and CSS conventions used in the prototype. This section is intended for engineers implementing or extending the system.

Core State Object

The eeProfile object tracks the current experience's brand kit and content profile state. It's the single source of truth for the design bar and canvas mode.

var eeProfile = { id: 'classic', // current profile id: 'classic' | 'premium' | 'minimal' | 'default' name: 'Classic', // display name of active shared profile shared: true, // whether a shared (account-level) profile is active count: 4, // number of experiences using this shared profile customized: false, // true = experience has its own custom profile customName: null // display name of the custom profile — always 'Custom' when set };

Content Profile Config Store

All content profile settings are stored in profileConfigs, keyed by a string that matches the navigate route. (Variable and route names use the kit prefix for historical reasons — they refer to content profiles, not Brand Kits. Renaming these is a candidate follow-up.)

var profileConfigs = { 'profile-editor-classic': { name: 'Classic', desc: 'Standard booking flow for most experiences', btnLabel: 'Request Booking', headerColor: '#3d3d3d', btnColor: '#3D57FF', btnRadius: 8, experiences: ['Painted Ladies Tour', 'Culinary Adventures', ...] }, // 'profile-editor-premium', 'profile-editor-minimal', 'profile-editor-new' // Custom profiles are registered here dynamically on creation: 'profile-editor-custom-painted-ladies': { /* ...inherited from classic */ } };

Key Functions

navigate(page)
Central router. Hides all pages, shows the target page, sets active nav state. Handles all page keys including profile-editor-*, brand-editor-*, experience-edit, branding, kits, etc.
eeUpdateProfileUI()
Reads eeProfile and syncs every UI element — design bar name, CTA visibility, pill background, canvas class. Called after any state change to eeProfile. This is the single re-render function for the design bar.
eeSetView(name)
Switches panels inside the experience editor: 'custom' (editor), 'branding' (brand kit switcher), 'profile' (content profile switcher). Does not navigate away from the experience editor page.
createProfileConfirm()
Handles the modal confirm action. Auto-generates a profile name and description, registers the new profile in profileConfigs, inserts a card into the profile switcher, sets eeProfile.customized = true, calls eeUpdateProfileUI().
kitReturnToGlobal()
Renders the "Profile Settings" panel in the profile editor — name field, description textarea. Reads from profileCurrentCfg. Called on profile editor load and when navigating back from a section panel.
eeSelectProfile(el, id)
Called when a profile card is selected in the switcher. Updates visual selection, syncs eeProfile fields, calls eeUpdateProfileUI() and eeApplyContentProfile().
eeOpenPanel(key)
Opens a settings section panel in the experience editor. Guards against preview mode — if the canvas has the .preview-mode class (the CSS implementation of preview mode), the call is a no-op (shared profile is active, canvas is locked).

Design Decisions

This section records the reasoning behind key UI and design decisions in the Branding prototype. The goal is to give future contributors — human or AI — enough context to maintain consistency without relitigating resolved questions.

One Panel, Two States

Decision: The experience editor uses a single panel element (#eeCustomizePanel) that serves two purposes: the "Profile Settings" home state when a custom profile is active, and the section editor state when a canvas section is clicked.

Why: An earlier implementation added a separate <aside> panel alongside the canvas. This broke the layout (the panel started above the topbar) and created inconsistency with the account-level profile editor, which uses one persistent panel throughout. The unified approach was adopted to match that pattern exactly.

Rule: Never add a second panel element. Sections navigate "into" the single panel; the back button returns to Profile Settings.

Neutral Gray Pills in the Design Bar

Decision: Design bar pills use neutral gray (#f4f5f7) backgrounds, not blue or indigo.

Why: Blue pills implied an "active selection" state that confused users — it read as "this item is selected/active" rather than "this is the current value." Gray reads as an informational chip. Hover states use a slightly darker gray to signal interactivity.

Whole Pill Is Clickable (Not a Button Inside)

Decision: The entire design bar pill is the click target, not a small "Switch" button embedded inside it.

Why: An earlier version had a separate "Switch" button inside each pill, which reduced the click target and added visual noise. Making the whole pill clickable is cleaner and more consistent with how chips work in the rest of the app. A chevron icon signals interactivity.

"Customize for this Experience" Lives in the Switcher

Decision: The "Customize for this experience" CTA is inside the profile switcher panel, not in the design bar itself.

Why: Putting it in the design bar cluttered the bar and exposed the action too prominently. The switcher is the right context — the user is already browsing profiles when they decide to customize. It also disappears naturally once a custom profile exists, without needing to manage a separate visible/hidden state in the bar.

Content Profile Cards Are Not Clickable

Decision: Content profile cards in Branding Settings are static — clicking the card does nothing. Actions (Edit, Set as Default, Delete) are exposed via a ··· menu.

Why: An earlier version made the entire card a clickable link to the kit editor. This caused accidental navigation and was inconsistent with brand kit cards, which use the same ··· pattern. Standardizing on the menu pattern makes both sections feel like one coherent system.

Custom Profile Naming: Always "Custom"

Decision: Experience-scoped custom profiles are always named "Custom", not derived from the experience name.

Why: Experience names change over time. A name like "Custom (Painted Ladies Picnic & Architecture Tour)" would become stale immediately if the operator renames the experience. "Custom" is always accurate regardless of what the experience is called. The backend can use stable key identifiers for association; the display name stays simple.

Canvas Locking in Preview Mode

Decision: When a shared profile is active, the canvas enters preview mode — implemented by adding the CSS class .preview-mode to #eeCanvas. This hides edit affordances and makes eeOpenPanel() a no-op.

Why: Shared profiles are used by multiple experiences. Allowing direct canvas edits would give no indication of scope — the user could unknowingly change a profile affecting dozens of experiences. The locked canvas forces the operator through the profile editor, where the scope warning (amber banner) is always visible.

State Restoration Uses profileConfigs, Not eeProfile

Decision: On re-entry to the experience editor, eeInit() checks profileConfigs to determine whether a custom profile exists — not the eeProfile state object.

Why: eeProfile is session state that was being reset to defaults on every navigation. This caused the "Customize" button to reappear after the user created a custom profile, navigated away, and came back. profileConfigs persists within the JS session and is the authoritative record of what profiles exist.

Topbar Layout Matches Account Level

Decision: The experience editor topbar has the viewport toggle on the left, hint text on the right, and no "Open full preview" link.

Why: An earlier version had the viewport toggle on the right with a preview link, and a pill badge for profile context. The account-level profile editor has a cleaner layout with the toggle on the left. Matching it exactly creates a consistent experience across both editors and removes UI elements that users found confusing or unnecessary.

Brand Kit Wordmark Styling

Decision: Brand kit cards that have no logo uploaded display the kit name as plain text — font-weight: 600 only. No uppercase, no letter-spacing, no italic, no decorative font.

Why: Heavy styling (italic Georgia, uppercase with letter-spacing) implied the text itself was a designed logotype. It is not — it is a placeholder shown when no logo exists. Plain text makes the absence of a logo obvious and avoids creating a false impression that the styling is intentional brand design.

Chapter 7
Glossary
Quick reference for terminology used across this system.
Brand Kit
A named set of visual settings (logo, brand name, header color, button color, link color) that controls the appearance of the booking page. Account-level, shareable across experiences.
Content Profile
A named configuration that controls the structure and behavior of the booking flow (CTA label, field visibility, layout). Can be shared or experience-scoped.
Shared profile
A content profile managed in Branding Settings, assignable to multiple experiences. Editing affects all assigned experiences.
Custom profile
An experience-scoped content profile created from the Experience Editor. Only affects the experience it belongs to. Does not appear in the account-level list.
Preview mode
The state of the experience editor canvas when a shared profile is active. Canvas sections are visible but not editable. Implemented via the .preview-mode CSS class on #eeCanvas.
Design bar
The horizontal control bar in the Experience Editor showing the active Brand Kit and Content Profile, with quick actions to switch either.
Profile switcher
The panel opened by clicking "Switch" in the design bar's Content Profile section. Lists all available profiles for the experience.
Scope warning
The amber banner shown in the profile editor indicating how many experiences will be affected by a save action.
eeProfile
The JS state object tracking the current experience's active profile state. The single source of truth for the design bar and canvas mode.
profileConfigs
The JS data store containing all content profile configurations, keyed by route string (e.g., 'profile-editor-classic').
